1. System architecture

Every day Airflow pulls BTC-USD OHLCV data from Yahoo Finance (2017 → today, 3,585 usable rows), builds 14 scale-free features (1-day return, 7/30-day moving-average ratios, 7/30-day volatility, 7 lagged close ratios, high–low range, volume change) and trains a direct multi-horizon XGBoost model: seven regressors, one per horizon h = 1…7, each predicting the log-return from today's close to day t+h. Predicting returns instead of raw prices lets trees forecast prices they have never seen. The model is back-tested on the most recent 7 days (train on everything before, forecast, compare) and is only promoted to model.pkl if MAPE ≤ 10%; Flask is then told to reload. The same steps exist as a Kubeflow pipeline. Code is linted, tested and shipped by GitHub Actions to GHCR and deployed on Minikube.

Part A — Flask REST API microservice

EndpointBehaviour
GET /healthstatus: ok, uptime, loaded model version/stage, training date. Used by K8s liveness & readiness probes.
POST /predictOptional forecast_days (int 1–7, default 7) and optional history (≥ 40 OHLCV records → features recomputed on the fly). Returns dated predictions.
GET /metricsMAE, RMSE, MAPE, naive-baseline MAPE and test window of the latest validation run.
POST /reloadRe-reads model.pkl; called by Airflow. Pods also hot-reload automatically when the file's mtime changes.

Validation & errors. Every error is JSON: 400 for non-JSON bodies, invalid JSON, non-object payloads, wrong-type or out-of-range forecast_days (incl. booleans/floats), short history, missing fields, negative prices or bad dates; 404/405 for wrong routes/methods; 503 when no model is loaded; a catch-all handler returns 500 without leaking a stack trace. Model loading is thread-safe (lock) and promotion uses atomic file replace, so a request never sees a half-written model. Gunicorn serves the app in production: gunicorn --bind 0.0.0.0:$PORT --workers 2 --timeout 60 app:app.

C2 Kubeflow. kubeflow/btc_kfp_pipeline.py (KFP SDK 2.18) defines four container components — ingest_data, generate_features, train_model, evaluate_and_register — each running the btc-pipeline image (kubeflow/Dockerfile). Kubeflow passes typed artifacts between them (Dataset → Dataset → Model + metrics → registered Model), so lineage is tracked; caching is off so each run fetches today's data, and the gate step fails the run if the model is rejected. The pipeline compiles to kubeflow/btc_kfp_pipeline.yaml (IR schema 2.1.0) in CI, and --schedule uploads it as a daily recurring run on a KFP cluster. To prove the compiled spec really runs, kubeflow/run_local.py reads each executor’s image, command and args from the YAML, fills the KFP placeholders and runs it with docker run, wiring artifacts between steps:

Performance analysis & issues found during deployment

Model. Back-test on 2026-11-18 → 2026-11-24: MAE $3,013, RMSE $3,291, MAPE 4.99% vs 6.71% for the naive “price stays flat” baseline. That week BTC fell sharply; the model followed the level but under-predicted the drop — expected for a daily-frequency model with no news/sentiment inputs, and why the promotion gate and daily retraining matter. One 7-day window is a noisy estimate; a rolling multi-window back-test would be the next improvement.

Serving & scaling. Inference is cheap (7 tree ensembles on one feature row): the median latency was 5 ms with 98,791 requests and 0.00% errors. Under 150 users the 2 baseline pods hit 354% of their CPU request; within one HPA sync the controller asked for 6 and then 8 pods (max), all of which became Ready and absorbed the load, bringing CPU down to ~170% (still above target, so the HPA correctly stayed at its ceiling). After the test it scaled down in steps (8 → 4 → 2) once the 60 s stabilisation window passed. The p95/p99 tail (240/630 ms) comes from the first ~60 s, before the new pods were Ready, while the 2 original pods were throttled at their 500m limit. An earlier run done while the Airflow stack shared the same Docker VM saturated the node (0.62% errors, see below) — a reminder that HPA can only add pods if the node has spare capacity; in production a Cluster Autoscaler would add nodes.
